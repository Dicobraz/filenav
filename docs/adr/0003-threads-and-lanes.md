# ADR-0003: потоки и полосы

Статус: принято (S1, 2026-10-14). Источник: specs/S1.md §0, §1. Уточнения: S0-contracts-v2 №7, v3 №7, v5 №6 (ADR-0004, 0006, 0008).

## Контекст

UI-поток владеет состоянием (ADR-0001) и не должен ждать I/O. Листинг не должен стоять в очереди за копированием 50 ГБ. В простое — 0% CPU.

## Решение

1. I/O-пулы делятся на две полосы: `Interactive` (4 потока: листинг, stat, превью) и `Bulk` (2 потока: короткие задачи операций, запись сессии). CPU-работа идёт в глобальный пул rayon на N−1 потоков, поэтому S4 вызывает `par_sort` без `install`.
2. Долгоживущие воркеры (ops, watcher, PTY-reader) создаются через `spawn_dedicated`. `Lane::Bulk` — только для коротких задач, ops сам ограничивает свои потоки `ops.max_threads`.
3. Каналы воркеры→core ограничены (1024 `Msg`). Send блокирующий, отмена проверяется каждые 50 мс. UI-поток никогда не вызывает `MsgSink::send` (`debug_assert!` по thread-id).
4. Прогресс передаётся атомиками, UI читает их напрямую. Пока есть активные задачи, перерисовка не чаще 30 раз/с.
5. Пробуждение коалесцируется через `WakeFlag`: `Waker::wake()` вызывается только при переходе false→true, флаг сбрасывается в начале `pump`. `MsgSink::poke()` будит UI без `Msg` через тот же флаг.
6. Паники в задачах перехватываются (`catch_unwind`), поток пула живёт дальше. Release-профиль — `panic = "unwind"`.
7. `Core::shutdown(200ms)` отменяет токены, закрывает каналы (заблокированные send просыпаются с `Closed`), ждёт join не дольше таймаута, затем отпускает потоки.

## Последствия

- Естественный бэкпрешер без потери данных, ограниченная память, 0% CPU в простое.
- Быстрая навигация не ждёт операций, сортировка не мешает UI.
- Все потоки именованы, чтобы их было видно в профилировщике и crash-логах.
