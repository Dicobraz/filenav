# ADR-0017: финальный порядок большого листинга считает core по своим записям

Статус: принято (владелец, 2026-10-18, при S4-19; вариант `DoneUnsorted`). Закрывает issue #70.

## Контекст

Цель S4 §7 «пиковая память листинга 100k < 15 МБ» не выполнена: 17,5 МБ (рабочий набор). Причина — `VfsListing` держит в потоке листинга полную копию записей (`all`), пока core держит свои `entries`. Копия нужна, чтобы:
- раз в CHUNK·2^k записей присылать полный `Order` (геометрические пересорты, S4-06);
- в конце прислать финальный `Order` до `Done`.

Две копии по 48 Б на запись плюс пики роста `Vec`. На 100k это ~5–6 МБ лишнего, на 1M ~50–75 МБ (решение владельца 2026-10-18: для 1M — цель листинга < 110 МБ).

Эксперимент (S4-11): без копии и без пересортов — 10 МБ рабочего набора вместо 17,5, `t_sorted` 47 мс вместо 83.

Без изменения core это не сделать. Финальный порядок можно посчитать только по записям core. При refresh они лежат в приватном `Tab.incoming`, а `ListingUpdate::Done` сейчас значит «порядок уже окончательный»: по нему core показывает листинг и делает подмену при refresh.

## Решение (предложение)

1. **Новый вариант `ListingUpdate::DoneUnsorted`.** Значит: «все записи пришли, финальный порядок посчитай сам».
   - Получив его, core запрашивает `ListingService::arrange` по своему `Arc` записей. Копии нет: дописывание закончено.
   - `Complete` (и подмена при refresh) наступает, когда придёт `Order` на полную длину.
   - `Done` остаётся для листингов, где порядок уже окончательный: один чанк (первый чанк приходит отсортированным), `Unsorted`, FakeListing.
2. **`VfsListing` не держит копию.** Он считает только число записей (база индексов `visible`), промежуточные пересорты убирает. Для многочанкового каталога в конце шлёт `DoneUnsorted`.

## Альтернативы

- **Без нового варианта: core сам решает по числу чанков.** «Пришло больше одного — сортировать на `Done`». Контракт по типу тот же, но смысл `Done` меняется неявно. Труднее тестировать, FakeListing с несколькими чанками начнёт пересортировывать.
- **Оставить копию.** Цель 100k < 15 МБ не выполняется; на 1M уходит ~50 МБ лишнего.
- **Хранить записи блоками** (метод 2 из ответа владельцу). Меняет `Listing.entries`, это крупнее и копию в воркере не убирает.

## Последствия

- **Память.** На 100k ~10–13 МБ вместо 17,5; на 1M около −50 МБ. Цель «< 15 МБ» выполняется.
- **Время.** `t_sorted` на 100k ~55–60 мс вместо 83 (одна сортировка вместо геометрических). Плюс один круг сообщений: `DoneUnsorted` → `arrange` на cpu-пуле → `Order`.
- **Промежуточная сортировка пропадает.** Пока грузится большой каталог, хвост после первого чанка идёт в порядке прихода. На NTFS это почти порядок имён; при сортировке по размеру или дате хвост до конца загрузки не упорядочен. Refresh визуально не меняется: подмена ждёт финальный порядок.
- **Код.**
  - `urfin-core`: вариант `ListingUpdate::DoneUnsorted`, ветка в `apply_shown`/`apply_incoming`.
  - `urfin-vfs`: `stream` без `all`, `Resort` уходит; `Poller` получает снимок из `TabEvent::Left`/`Activate` иначе (сейчас — из `all`).
  - Тесты core и `list_is_resorted_while_streaming` переписываются.
