# ADR-0001: владение состоянием

Статус: принято (S1, 2026-10-14). Источник: specs/S1.md §0, §1.

## Контекст

Кадр должен укладываться в ≤2 мс при 100k строк, ввод применяется не позже следующего кадра. Состояние читают UI и handlers команд, а меняют его результаты фоновых задач (листинг, сортировка, операции).

## Решение

1. Состоянием владеет один объект `Core`, он живёт в UI-потоке. Handlers работают как редьюсеры над `&mut AppState`, UI в кадре читает `&AppState` напрямую. `Arc<RwLock>`, снапшотов и копий нет.
2. Handlers не делают I/O и не блокируются. Тяжёлое уходит в `Runtime::spawn*`, результат возвращается сообщением `Msg` и применяется в `Core::pump`. В debug-сборках handler дольше 1 мс даёт `tracing::warn!`.
3. Большие данные хранятся как `Arc<Vec<Entry>>` и `Arc<Vec<u32>>` (порядок). Воркер получает клон `Arc` за O(1), чанк добавляется через `Arc::make_mut`.
4. Устаревшие результаты отбрасываются по `Gen` (u64 на таб, растёт при каждой навигации). Предыдущая загрузка отменяется `CancelToken`.
5. `..` — виртуальная строка 0. Её нет в `entries`, и её нельзя выделить.

## Последствия

- Кадр без блокировок и копирования, латентность ввода ≤1 кадр, детерминированные тесты.
- Отвергнуто: отдельный core-поток с ArcSwap-снапшотами (+1 кадр задержки, копирование 100k строк).
- Копирование `entries` (~1 мс) случается только при гонке «чанк во время сортировки».
- Любой код, которому нужен I/O из handler, обязан идти через Runtime и `Msg` (ADR-0003).
